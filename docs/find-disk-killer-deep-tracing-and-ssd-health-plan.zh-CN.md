# FindDiskKiller 深度文件追踪与 SSD 健康方案（无特殊 entitlement）

> 文档状态：方案已签发；A/B 基线与文件访问追踪工程实现完成，发布与深度 Gate 待执行<br>
> 制定日期：2026-07-23<br>
> 最近修订：2026-07-24<br>
> 目标平台：macOS 14 及以上，Apple Silicon 与 Intel 进入支持矩阵<br>
> 适用产品：Developer ID 签名、公证并从官网分发的 FindDiskKiller<br>
> 约束：不申请 Endpoint Security entitlement 或其他 Apple 特殊 entitlement，不安装 Endpoint Security 系统扩展，不开发内核扩展<br>
> 优先级：响应优先、证据诚实、按需提权、默认保护路径隐私

这里的“无特殊 entitlement”不等于“完全无本机授权”。限时深度追踪仍需要管理员批准随 App 签名的后台辅助进程；受 TCC 保护的路径只有在用户确实需要时才引导完全磁盘访问。二者都是用户在本机做出的可撤销授权，不是向 Apple 申请能力。

本方案取代《FindDiskKiller macOS 磁盘 I/O 监控软件方案》中关于 Endpoint Security 路径归因、SSD 健康和相关权限流程的设计。旧方案的签发记录不自动适用于本方案；本方案只有在第 16 章列出的独立评审全部签发后，才能标记为“已签发”。

## 1. 产品目标

FindDiskKiller 已经能够回答“哪个应用正在消耗磁盘、CPU 和网络”。本阶段继续回答四个更深入的问题：

1. 某个应用当前正在访问哪些文件和目录？
2. 在用户主动开启的一段追踪时间内，它向哪些目录发起了多少读写请求？
3. 在用户选择的一段时间内，指定文件或目录收到多少读写请求，哪些文件和应用贡献最多？
4. 当前 SSD 已经承受了多少主机写入，设备报告的磨损、温度和错误状态如何？

产品仍然不是 Activity Monitor 的替代品，也不是文件审计或取证工具。它的差异化价值是把进程、路径、设备健康和时间上下文组织成用户可以直接理解的诊断结论。

### 1.1 核心用户任务

- AI Agent 持续写盘时，快速找到它正在操作的项目、缓存、日志或数据库目录。
- 构建、同步或下载任务导致磁盘繁忙时，确认涉及的目录和持续时间。
- 在 1、5 或 15 分钟的限时追踪中，比较各目录的读写请求总量、平均速率与峰值。
- 选择一个文件或目录，查看本次会话的请求读写总量、最近 5 秒速率、峰值、活跃文件和访问应用。
- 查看 SSD 累计主机写入、寿命消耗、温度、备用空间和介质错误。
- 判断最近持续写入是否显著高于个人历史，而不是把正常构建或下载误判为故障。

### 1.2 明确不承诺的能力

- 不声称常态模式可以精确计算“某进程向某目录写入了多少字节”。
- 不把 FSEvents 观察到的路径变化直接归因给某个进程。
- 不把 `fs_usage` 的请求字节等同于 SSD 最终物理落盘字节。
- 不保证受 SIP、权限或系统工具格式变化影响的进程始终能够被完整追踪。
- 不把 NVMe `Data Units Written` 称为 NAND 实际写入量。
- 不在设备未提供厂商属性时展示“擦写次数”。
- 不在缺少可靠 TBW 或磨损趋势时预测具体报废日期。
- 不提供文件访问阻断、进程终止、自动清理或后台持续记录完整路径。

## 2. 用户能够获得的功能

| 功能 | 默认可用 | 是否需要管理员授权 | 用户看到的口径 |
| --- | --- | --- | --- |
| 应用总读取/写入、当前/平均/峰值 | 是 | 否 | 进程自身的全盘 I/O 合计 |
| 当前打开的文件与目录 | 同 UID、当前实际可见进程及 TCC 可见目录可用 | 否 | “正在访问”，不显示目录字节数；不可见时显示覆盖缺口 |
| 文件以只读、只写或读写方式打开 | 当前用户可见进程可用 | 否 | “只读 / 可写 / 读写” |
| 最近发生变化的目录 | 是 | 否 | “系统观察到变化”，不声明进程归属 |
| 选中应用的限时深度追踪 | 按需 | 是，注册后由管理员在系统设置批准辅助进程 | 追踪到的读写请求字节；覆盖不足时不生成目录结论 |
| 应用相关目录的文件访问追踪 | 按需，全部 Gate 通过后提供 | 是，注册后由管理员在系统设置批准辅助进程 | 目录内所有应用向系统请求的读写量；不等于物理磁盘 I/O，也不默认声称由当前应用产生 |
| SSD 基础身份与 SMART 总体状态 | 设备支持时 | 否 | 系统报告的设备状态 |
| NVMe 累计主机写入、磨损、温度等 | 设备支持时 | 通常否 | 逐字段能力检测，不支持则不显示 |
| SATA/部分 USB 设备扩展 SMART | 可选兼容层 | 可能需要 | 仅在字段含义经过设备适配后显示 |

不存在一个“启用归因”的总开关。用户只会看到与当前任务直接相关的操作：

- `查看正在访问的位置`
- `开始深度追踪`
- `在应用文件活动中追踪此目录`
- `查看 SSD 健康`

若某项能力不可用，界面说明当前事实和下一步，不使用“待归因”“能力准备中”“高级功能未启用”等无法行动的措辞。

## 3. 数据来源与准确性边界

### 3.1 进程总 I/O

继续使用 `proc_pid_rusage` 等公开进程统计接口。它能够提供进程生命周期内的累计读写数据，并可按采样窗口计算当前、平均和采样峰值。

该数据代表进程自身的 I/O 统计，不等于某块物理设备的落盘量，原因包括缓存、内存映射、APFS、压缩、交换、网络文件系统和设备层合并。界面统一称为“应用全盘 I/O 合计”。

### 3.2 当前打开的文件

使用 macOS SDK 随附但头文件标记为 private、可能变化的 `libproc` 接口。它不需要特殊 entitlement，但只用于 Developer ID 站外版本，并按支持的 macOS 版本保存夹具；接口失配时降级为“文件位置不可用”，不能影响基础监控：

1. `PROC_PIDLISTFDS` 获取进程文件描述符列表。
2. 对 vnode 描述符调用 `PROC_PIDFDVNODEPATHINFO`。
3. 从 `vnode_fdinfowithpath` 获取路径、文件类型、设备标识、文件大小与 `fi_openflags`。
4. `fi_openflags` 实测使用内核 `FREAD/FWRITE` 位语义，不能套用用户态 `O_ACCMODE`；先识别 `O_EVTONLY`，再按 `FREAD`、`FWRITE` 或两者同时存在区分只读、只写和读写。打开模式固定为“只读 / 只写 / 读写 / 仅事件通知 / 未知”，仅事件通知不能作为数据读取证据。每个支持的 macOS 版本必须用受控 FD 夹具重新验证该 private 结构语义。

它能够证明采样时刻进程持有该文件，但不能证明采样间隔内实际发生了读取或写入，也不能给出每个文件的 I/O 字节数。界面必须使用“正在访问”“以可写方式打开”，不能使用“正在写入”作为唯一结论。

### 3.3 最近路径变化

使用 FSEvents 观察各本地卷的目录树变化。它适合回答“哪些位置最近发生变化”，但事件可能合并到目录层级，不包含可靠进程身份，也不包含写入字节数。

常态模式允许把以下证据并列展示：

- 进程以可写方式打开了该目录下的文件。
- 同一时间窗口内，该目录发生了系统观察到的变化。

界面可显示“该应用正在访问；目录最近发生变化”，但不得合并成“该应用写入了该目录”。

### 3.4 限时深度追踪

特权辅助进程按用户选择调用系统自带的：

```text
/usr/bin/fs_usage -w -f filesys -f pathname -t <秒数> <PID 或命令>
```

必须使用 `posix_spawn` 或等价参数数组启动，禁止通过 shell 拼接用户输入。允许的时长固定为 60、300、900 秒。首版只追踪用户明确选中的应用，不提供全机深度追踪。

根据当前 macOS 手册，`fs_usage`：

- 使用内核 tracing facility，要求 root 权限。
- 可以提供调用时间、系统调用、文件描述符、请求字节数、路径、偏移和进程/线程标识。
- `B=x` 表示该系统调用请求的字节数，不保证等于最终物理落盘量。
- 输出格式会受系统版本影响，PATHNAME 最多可能只保留路径末尾 28 bytes，SIP 或系统保护也可能造成缺口。

追踪开始时记录选中应用组的 PID 与启动时间，并把这一组 PID 作为过滤条件。追踪中新增的子进程不能静默算作已覆盖：宿主每秒更新应用成员，结果顶部显示 `已覆盖 10/12 个应用进程`。若未覆盖进程贡献了超过应用组 1% 或 1 MB 的进程 I/O（取较低门槛），本次结果标记为不完整，并取消“主要集中在某目录”的自动结论。阶段 C 可以验证分段重启追踪以纳入新 PID，但每次重启产生的时间缺口必须保留，不能插值。

相同进程会话、相同 FD 的 `libproc` 快照只能补全部分 read/write 类记录；rename、unlink、快速 FD 复用或没有稳定 FD 的记录不能猜测补全。因此阶段 C 是可行性 Gate，而不是已承诺交付的产品功能。Gate 未通过时只发布阶段 A/B。

所有通过 Gate 的数值统一命名为：

- `读取请求`
- `写入请求`
- `请求平均速率`
- `请求峰值`

不得缩写成容易误解的“实际写入”或“目录写入量”。只有系统调用成功、PID 会话身份一致、文件描述符路径映射明确的记录才能进入目录数值聚合。错误、无法映射、截断且无法补全的记录进入“未定位请求”。

#### 3.4.1 指定文件或目录的文件访问追踪

指定目标模式的产品名称固定为“文件访问追踪”，不使用“物理写入归因”。它回答：本次会话捕获到多少读取请求和写入请求、最近 5 秒请求平均速率、1 秒桶请求峰值、哪些目标内文件贡献最多，以及哪些经过身份验证的应用进程发起了请求。

这些数字始终是应用向系统调用提交的请求量。缓存命中读取可能不产生物理盘读取；APFS 缓存、压缩、CoW、元数据和延迟写回会让设备实际写入不同；`mmap` / page fault 也不保证以可定位的 read/write 记录出现。因此该页面不得与设备吞吐配平，不得推导 NAND 写入量，也不得把 FSEvents 变化数量换算为字节。

当前 `fs_usage` 没有路径过滤参数。指定目录若要发现所有访问应用，helper 必须读取全机文件系统事件流。现实现选择更小的 root 攻击面：App 不把目标路径传给 helper；helper 只执行固定命令并通过有界 XPC 批次返回内存中的原始行与已经验证的进程身份，路径规范化、卷身份校验和目标匹配全部在普通用户权限的 App 进程完成。原始行不落盘、不进入普通日志，停止、超时、App 断开或缓冲过载时立即终止或标记缺口。全机流的事件速率、隐私范围和 CPU 成本仍明显高于按 PID 追踪，必须单独通过 TRACE-SECURITY、TRACE-DATA 和 TRACE-PERF。

`fs_usage` 手册明确宽格式进程字段附加的是线程 ID，不能把末尾数字直接解释为 PID。现 helper 使用 `PROC_PIDLISTTHREADS` 映射线程，并通过 `proc_pid_rusage(... RUSAGE_INFO_V4 ...)` 固化 `PID + 启动时间`；映射失败时只增加身份覆盖缺口，不生成伪进程排行。受控 fixtures 已覆盖协议与 fail closed，但仍不能替代安装 helper 后的真实系统版本格式、路径召回和事件风暴 Gate。

目标由系统选择器产生，并在主 App 与 helper 两侧验证为绝对文件 URL、稳定卷身份和文件/目录类型。目录匹配使用路径组件，不使用字符串 `hasPrefix`；`/foo` 不能匹配 `/foobar`。符号链接只在选择时和事件处理时都取得可验证解析路径时合并；硬链接通过目标树之外的另一路径访问时不猜测为同一文件。rename、unlink、无路径 FD、截断路径或卷身份缺失均进入覆盖缺口，不能计入目标总量。

### 3.5 四种证据标签

全产品只使用以下四个标签，不使用抽象的“高/中/低置信度”：

| 标签 | 用户含义 | 是否显示目录字节数 |
| --- | --- | --- |
| 正在访问 | 进程当前打开该位置 | 否 |
| 最近变化 | 系统观察到目录变化，未确认进程 | 否 |
| 本次追踪 | 限时追踪捕获到进程、调用、路径和请求字节 | 是，明确标注“请求” |
| 未定位 | 捕获到进程请求，但路径无法安全确定 | 只计入总量，不分配目录 |

这四个标签在列表、图表、悬停说明、导出和辅助功能中保持同一含义。

## 4. 系统架构

```text
FindDiskKiller App
  ├─ MonitorStore                  现有 CPU / 磁盘 / 网络 / 进程采样
  ├─ OpenFileSampler              libproc 文件描述符快照
  ├─ FileChangeWatcher            FSEvents 目录变化
  ├─ FileActivityCorrelator       证据并列与目录聚合
  ├─ DiskHealthStore              SMART 能力模型与历史
  └─ TraceSessionController       用户发起的限时追踪
           │
           └─ XPC（签名与 audit token 校验）
                 │
                 └─ FindDiskKillerTraceHelper（root）
                      ├─ 启动并监管 fs_usage
                      ├─ 流式解析与版本自检
                      └─ 返回结构化记录，不返回任意命令输出
```

### 4.1 OpenFileSampler

- 后台常态采用有界轮转采样，不在每一轮遍历全部进程和全部 FD。
- 当前高 I/O 进程、可见列表与用户打开的详情优先；其余当前用户进程分批轮转。
- 打开某个进程详情时，该应用组提升到每 1 秒扫描；常态目标覆盖周期为 5 秒，但性能预算优先于覆盖周期。
- 离开页面后立即恢复低频，不让 UI 页面决定数据是否存在。
- 使用 `PID + 启动时间` 作为会话身份，避免 PID 复用串数据。
- 同一应用的 helper 默认聚合到签名宿主；展开后显示原始 PID。
- 每轮分别限制 PID 数、单 PID FD 数、总 syscall 数和 250 ms 时间预算；C 层从进程身份校验前开始计时，在每个可中断边界停止并把结果标为不完整。单次 `libproc` 系统调用无法被安全抢占，因此 250 ms 是跨调用的停止预算，不承诺杀死正在执行的单次系统调用。
- 每个结果携带实际覆盖时间。未轮到、超限或部分失败时显示“仅显示部分打开位置 · 更新于 5 秒前”，不能把未扫描显示为空。
- 路径权限错误不重试风暴，不把不可见显示为“没有文件活动”。

### 4.2 FileChangeWatcher

- 每个本地可写卷建立独立 FSEvent stream，并在支持时请求 FileEvents 标志。
- 事件延迟目标为 1 秒，批量合并到目录级 1 秒桶。
- 处理 MustScanSubDirs、UserDropped、KernelDropped、EventIdsWrapped 和 RootChanged。
- 发生丢弃后，该时间段显示缺口；重新建立基线前不推断目录变化连续性。
- 网络卷、只读卷和磁盘镜像按运行时能力单独标记，不套用本地卷结论。
- 默认先验证目录级事件能否满足产品任务，只有确需文件级变化时才启用 FileEvents 标志。
- 对构建目录和大型卷的事件风暴按目录与 1 秒桶合并；超过内存或处理预算时扩大延迟并显示覆盖缺口，不追赶无限积压。
- 卷卸载时结束对应 stream 并保留结束时间；重新挂载后建立新基线，不把中间时间解释为无变化。
- 只为本地可写且具有稳定身份的卷建立 stream；只读卷和无法稳定识别的卷明确显示“当前卷不可观察”。运行中的详情任务以卷身份、规范化挂载点、可写状态和身份能力作为拓扑身份，任一变化都会销毁旧 stream、清除该卷内存历史并建立新基线。
- 卷身份优先使用 volume UUID，其次使用系统 volume identifier；二者都不可得时，挂载路径只用于本轮 UI 关联并标记为不可观察，不能作为 FSEvents 历史身份，避免同一路径换盘继承旧事件。

### 4.3 TraceSessionController

追踪状态机固定为：

```text
未注册 → 等待用户确认 → 注册中 → 等待管理员批准 → 可用
                                              ↓
                                         正在准备 → 正在追踪 → 已完成
注册中/等待批准/正在准备 → 无法使用
正在追踪 → 用户停止 → 已完成（提前结束）
正在追踪 → 解析失配/辅助进程退出 → 结果不完整
```

状态文案必须回答三个问题：现在发生什么、用户是否需要操作、已有数据是否仍可信。例如：

- `等待你在系统设置中允许 FindDiskKiller 后台项目`
- `辅助进程已可用，正在准备追踪，通常不到 2 秒`
- `正在追踪 Codex，还剩 04:18`
- `已提前停止，已记录的 01:42 可以查看`
- `本次结果不完整：系统追踪格式无法识别，未生成目录数值`

解析器启动后先执行短自检，确认当前 macOS 输出中的时间、调用、进程/线程标识、FD 和 `B=` 字段。线程无法映射到已验证的应用进程会话时，该记录只能进入“未定位请求”。任何核心字段无法识别时 fail closed：结束会话、不显示部分伪精确数值、保留可读故障原因。

### 4.4 FileActivityCorrelator

- 标准化 `~`、APFS Data 卷前缀和符号链接显示，不改变原始文件身份。
- 用 vnode 的设备号映射用户卷名，不把物理设备吞吐复制到目录。
- 追踪记录优先使用事件中的完整路径；路径截断时只允许用同一已验证进程会话、同一 FD 的 libproc 快照补全。
- 不根据相同文件名、相近时间或目录变化猜测路径。
- 目录聚合默认到用户可理解的稳定边界，例如项目根、应用支持目录、缓存、日志、下载和数据库目录。
- 用户可以展开到文件；列表默认不一次绘制数万行。
- 所有平均值以完整选择时长为分母，峰值显示实际桶粒度，例如 `82 MB/s · 1 秒桶`。

## 5. 主要交互设计

### 5.1 进程详情中的“文件活动”

进程详情顶部使用一级分段控制 `概览 / 文件活动`。`概览` 保持现有 CPU、磁盘 I/O 和网络图表；`文件活动` 独立承载目录任务，不能被放到图表之后或首屏以下：

```text
进程详情    [概览] [文件活动]
文件活动    [正在访问] [追踪结果]
```

`正在访问` 默认立即出现，表格列为：

| 列 | 内容 |
| --- | --- |
| 位置 | 用户友好目录名，第二行显示缩略路径 |
| 打开方式 | 只读、可写或读写 |
| 打开文件 | 当前文件数量 |
| 最近变化 | 相对时间；没有变化证据时显示 `未观察到` |
| 所在卷 | `Macintosh HD`、`JianDisk` 等用户卷名 |

这里不出现 `0 B`，因为系统没有测量目录字节。该区域必须区分正在扫描、完整扫描且没有普通文件、部分结果（FD/时间预算耗尽）、路径受保护而部分不可见、进程已结束。只有完整扫描成功后才能显示“当前没有观察到”；部分结果保留已取得的数据并显示实际覆盖时间，不能渲染为空表或 `0`。

完整扫描后无打开文件时显示：

> 当前没有观察到该应用持有的普通文件。应用可能暂时空闲、使用内存映射，或尚未打开普通文件。

受保护路径必须归入“部分结果”或“当前无法读取”，不能作为完整空结果的解释。

`追踪结果` 顶部提供会话选择器，例如 `最近一次 · 今天 14:30 · 5 分钟`。没有会话时显示简洁操作区：

> 需要确认目录读写请求量时，可进行一次限时追踪。追踪期间只在本机处理路径。

主按钮为 `开始深度追踪`，旁边用菜单选择 1、5、15 分钟。不要在空状态中展示无效图表或全部为零的表格。

### 5.2 追踪中的反馈

开始后不打开阻塞式进度弹窗。页面顶部出现固定高度状态条：

```text
正在追踪 Codex      04:18     [停止并查看]
```

- 原有侧边栏、时间切换和其他页面仍可点击。
- 用户离开页面后追踪继续，侧边栏“应用”旁显示小型进行中指示。
- 返回时直接恢复当前进度，不重新加载空白页。
- 用户关闭主窗口时不弹窗；菜单栏面板可看到并停止会话。
- 同一时间只允许一个深度追踪，避免多重 root tracing 和解释冲突。
- 另一应用已在追踪时，入口显示 `正在追踪 Codex · 查看进度`，不能只禁用按钮而不给原因。
- 追踪只包含开始时已确认的应用进程；新增成员会即时反映到覆盖说明，不能被悄悄遗漏。
- 追踪期间应用退出时保留已捕获结果并结束对应成员；应用以新启动时间重启后作为新成员明确计入覆盖，不继承旧 PID 会话。
- App 退出、helper 更新、被用户关闭或重新批准后，恢复页必须说明本次会话是已完成、提前结束还是结果不完整。
- 详情不能禁用或遮挡侧边栏。追踪开始后允许离开详情，并通过侧边栏与菜单栏的全局进行中入口返回。
- 停止操作立即进入幂等的“正在停止”，不接受重复停止；已捕获数据继续固化。

### 5.3 追踪结果

结果顶部先给结论，不用实现术语：

> 过去 5 分钟，Codex 的写入请求主要集中在项目缓存和 Git 数据；另有 18.4 MB 请求未能定位到完整路径。

结论上方固定展示时间范围、目标应用、覆盖进程数、路径覆盖率和提前结束/缺口状态。路径覆盖低于 95% 时取消目录集中结论；“未定位请求”同时显示绝对量与占比。

表格固定展示：

| 位置 | 读取请求 | 写入请求 | 请求平均 | 请求峰值 | 文件 | 最后活动 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `~/Projects/find-disk-killer/.git` | 182 MB | 1.42 GB | 4.85 MB/s | 91 MB/s | 37 | 3 秒前 |

表格规则：

- 默认按写入请求降序，所有数值列支持升降序。
- 悬停一行后暂停当前排序刷新；完成会话的结果本身不再跳动。
- 点击目录展开文件，再次点击收起；双击或上下文菜单可在 Finder 中显示。
- 路径列可调整宽度并持久化，数值列保持稳定最小宽度。
- 长路径中间截断，悬停显示完整路径的小型不透明提示卡。
- `未定位请求` 是独立末行，不能混入已知目录。
- 表格总量必须等于本次被解析并纳入的请求量；设备吞吐不参与配平。

### 5.4 图表

追踪结果提供一张全宽目录请求趋势图，而不是为每个目录堆叠小卡片：

- 读取使用青色实线，写入使用橙色虚线。
- 使用直线折线，不使用平滑曲线。
- 默认展示总追踪请求；选择目录后高亮该目录并降低其他序列对比度。
- 鼠标提示跟随采样点并靠近指针，根据边缘自动避让。
- 提示卡为 100% 不透明背景，宽度随内容但设最大值，不覆盖指针。
- 提示内容只有时间、读取请求速率、写入请求速率和目录名。
- 图表下提供等价数据表和 VoiceOver 摘要。

### 5.5 点击、悬停和刷新

- 行的整个可见区域都是点击目标，悬停说明层必须 `allowsHitTesting(false)`。
- 悬停卡绘制在整个表格最上层，后续行不得覆盖其背景或文字。
- 点击行时第一帧立即显示选中底色，再打开详情，不等待新采样。
- 点击详情窗体外关闭详情；窗体内部点击不误关闭。
- 列表悬停时冻结行顺序，但后台采样继续；鼠标离开后一次性应用最新排序。
- 骨架屏与真实页面使用相同工具栏、表头、列宽和行高，并且不能阻止侧边栏切换。

### 5.6 应用文件活动内的目录追踪工作区（通过 Gate 后）

入口只放在“应用详情 → 文件活动”。左侧目录列表与右侧详情遵守标准主从交互：点击任意目录行只更新右侧详情，绝不触发页面跳转；用户在右侧确认目标后，再通过明确的“追踪此目录”按钮进入工作区。已有会话的目标显示“查看追踪”。磁盘页不展示该入口，避免用户误解为物理磁盘级追踪。

工作区首帧显示目标名称、遮挡用户名后的路径、会话状态、已运行时间和覆盖状态，并提供稳定的“返回文件活动”操作。返回不阻塞导航，当前窗口仍显示可重新进入的会话快捷条；若正在追踪其他目录，新目录操作保持禁用并直白提示先停止当前会话，不静默切换或丢弃结果。每个应用详情窗口独立持有自己的追踪会话和界面状态，不会在不同应用窗口之间错误复用目标或结果。若 helper 尚未获批，权限步骤作为页面内单一操作显示，不使用阻塞弹窗。

首屏使用响应式普通布局展示累计读取请求、累计写入请求、最近 5 秒读取/写入请求平均速率和会话峰值。图表沿用青色读取实线与橙色写入虚线；“最活跃文件”和“访问应用”使用稳定身份、可排序且列宽可调的列表。空闲完整覆盖时写“当前没有观察到读写请求”，不能写“没有磁盘活动”；覆盖不完整时持续显示原因、丢弃事件数和最后事件时间。

用户可随时停止、重新开始、返回目录列表选择新目标和清除结果。完整路径默认只存在于当前会话内存，停止后可以立即清除；持久化和导出默认关闭完整路径并遮挡用户名。所有相关正文使用“应用向系统请求的读写量”。工作区必须明确说明它观察该目录内所有应用的请求，不只限于打开详情的应用，并用“访问应用”列表确认实际参与者；缓存、CoW、写回和物理盘差异放在稳定说明中。该工作区和 10 种语言文案只有在全部 Gate 通过后进入正式构建；Gate 前不展示无效入口或无法完成的授权步骤。

## 6. 权限与安装体验

### 6.1 默认模式

应用首次启动不申请管理员权限。进程总 I/O、当前用户可见的打开文件、FSEvents 和多数 NVMe SMART 数据直接工作。

只有用户第一次点击 `开始深度追踪` 时，才解释：

> 深度追踪需要一个本机辅助进程读取系统文件调用。它只在你主动开始的限时会话中运行，不会阻止或修改文件操作。

操作只有：

- `继续安装`
- `暂不使用`

注册完成但处于 `requiresApproval` 时，在页面内显示：

> FindDiskKiller 辅助进程已经准备好，还需要你在系统设置中允许这个后台项目。批准前，基础监控仍可继续使用。

操作为 `打开登录项设置` 与 `继续使用基础功能`。返回前台后自动复检 `SMAppService.status`，不要求用户点击“已完成”，不循环弹窗。若 App 不在 `/Applications`、helper 未找到或版本需要更新，分别给出可执行的修复说明。

不要提供无法解释的 entitlement、系统扩展或“归因引擎”术语。

### 6.2 特权辅助进程

- 使用 `SMAppService` 注册随应用签名的 privileged helper。
- 宿主与 helper 使用同一 Team ID、Hardened Runtime 和版本协议。
- XPC 服务验证连接方 audit token、代码签名与协议版本。
- helper 只接受固定时长与固定追踪类型；指定目标模式下不接收任何目标路径、任意命令或任意 `fs_usage` 参数，路径与卷身份验证由普通权限 App 完成。
- helper 从 XPC audit token 解析调用用户 UID，并自行确认每个 PID 属于该用户。
- helper 在 root 侧重新读取并核对 `PID + 启动时间`，不能信任宿主提供的“已验证”结论。
- 固定限制单次 PID 数、会话时长、并发数、输出速率、缓冲区和 XPC 消息大小；超限时 fail closed。
- 进程退出、用户停止、超时或宿主断开时终止 `fs_usage` 子进程；系统睡眠/唤醒回收仍属于 TRACE-SECURITY 实机 Gate，验证前不宣称已覆盖。
- 注销、快速用户切换和另一用户请求追踪时结束现有会话，不跨用户共享 PID、路径或结果。
- helper 不写普通日志中的完整路径，不建立长期原始事件数据库。

这需要用户本机管理员确认，但不需要 Apple 专门审批的 Endpoint Security entitlement。

### 6.3 完全磁盘访问

完全磁盘访问不能由应用代替用户授予。只有检测到路径因 TCC 保护持续不可见、且用户正在使用路径功能时，才在页面内显示一次说明：

> 部分受保护目录未显示。你可以继续使用现有结果，或在系统设置中允许 FindDiskKiller 查看这些位置。

提供 `打开系统设置` 和 `继续使用`。应用返回前台后自动复检，不要求用户点击“我已完成”，不循环弹窗。拒绝授权不影响现有 CPU、磁盘、网络与 SSD 页面。

辅助进程批准与完全磁盘访问是两个独立能力状态：前者只影响限时追踪，后者只影响确认可由 TCC 改善的受保护路径。其他用户进程、SIP 或数据源自身缺口不得误导为可通过完全磁盘访问修复。真正读取路径的是 helper 或 `fs_usage` 时，必须使用签名公证构建在干净系统上验证 TCC 的实际授权主体；验证完成前不发布对应权限文案。

### 6.4 设置页

设置中只保留用户能够理解并直接控制的项目：

- 文件活动历史：不保留、24 小时、跟随普通历史保留期。
- 文件级明细：会话结束后保留 15 分钟或立即清除。
- 导出隐私默认值：完整路径、用户名、命令行、设备序列号，均默认关闭。
- 深度追踪辅助进程：显示“未注册 / 等待管理员批准 / 可用 / 被关闭 / 需要更新 / 无法使用”，安装后提供“打开登录项设置”与“移除辅助进程”。
- `立即清除文件活动历史`。

不提供“启用归因”“提高准确度”“高级扫描”等总开关。SSD 健康数据在设备支持时自动出现，不要求用户寻找设置开关。

## 7. SSD 健康数据方案

### 7.1 首选数据源

首版优先解析：

```text
/usr/sbin/diskutil info -plist <whole disk>
```

本机 macOS 已验证该结构可以在支持的 NVMe 设备上返回：

- `SMARTStatus`
- `SMARTDeviceSpecificKeysMayVaryNotGuaranteed`
- `DATA_UNITS_READ_0/1`
- `DATA_UNITS_WRITTEN_0/1`
- `PERCENTAGE_USED`
- `AVAILABLE_SPARE`
- `AVAILABLE_SPARE_THRESHOLD`
- `TEMPERATURE`
- `CRITICAL_WARNING`（仅在设备实际提供时使用；温度位由设备固件判定）
- `POWER_ON_HOURS_0/1`
- `POWER_CYCLES_0/1`
- `UNSAFE_SHUTDOWNS_0/1`
- `MEDIA_ERRORS_0/1`
- `NUM_ERROR_INFO_LOG_ENTRIES_0/1`

字段容器名称已经明确提示“设备特定键可能变化且不保证”。实现必须建立逐字段 capability model，不能因为字典存在就假设所有型号语义相同。

NVMe 语义不能只依赖 `BusProtocol`。内置盘通常报告 `NVMe` 或 `Apple Fabric`，但雷电/USB4 直通的 NVMe 可能报告 `PCI-Express`。解析器只有在总线明确包含 `NVMe` / `Apple Fabric`，或 `DeviceTreePath` 明确包含 `IONVMeController` 时，才按 NVMe 规则解释详细字段；不能仅凭 `PCI-Express` 判定。若设备树确认 NVMe 控制器且 `Internal = false`，界面使用“外接 NVMe（雷电/USB4）”这类用户可理解的连接名称，同时保留原始总线值作为诊断证据。

DiskHealthStore 不以可能变化的 `disk0`、`disk4` 作为长期主键。序列号、控制器唯一标识等组成强身份，经本地 HMAC 后允许跨重启保存趋势；只有设备树位置、型号和容量时属于弱身份，只维持本次启动或本次连接会话。无法确认强身份时不得跨重启计算磨损增量，也不得让同型号同容量的替换设备继承旧盘历史。健康页面可见时最多每 30 秒刷新一次，后台每 30 分钟刷新一次；读取失败显示最后成功时间，不把失败解释成设备故障。

健康对象始终是物理 whole disk，不是 APFS 卷。同一物理盘的 SMART 结果只展示一次；多卷不得复制健康结论，多物理盘组成的存储集合不得合成为单一健康度。卷页面提供清晰的“查看物理设备健康”入口。

### 7.2 数值转换

- `_0` 与 `_1` 组合为无符号 128 位计数；必须处理溢出，不能只读取低 64 位。
- NVMe Data Unit 按标准换算为 `512,000 bytes`，展示为十进制 TB；详细说明可同时提供 TiB。
- `TEMPERATURE` 只有在 provider 确认设备类型、字段语义与单位，且原始值位于合理 Kelvin 范围时才换算为摄氏度。温度是否异常只采用设备报告的 NVMe `CRITICAL_WARNING` 温度位或设备自带阈值，不由 FindDiskKiller 套用跨型号的通用温度线。
- `PERCENTAGE_USED` 是设备估算的寿命消耗整数百分比，可能超过 100；不得把 0 显示为“全新”或绝对“健康度 100%”。
- 原始值为 0 时显示 `设备报告寿命消耗低于 1%`，并说明设备只按整数百分比报告。
- `SMARTStatus = Verified` 只表示设备当前没有报告 SMART 失败，不代表不会发生故障。
- `DATA_UNITS_WRITTEN` 是主机写入，不是 NAND 写入，也不包含可直接解释的写放大。
- 每个字段保存来源、采样时间、能力状态和原始值类型。字段缺失、类型变化或 `diskutil` 格式失配时隐藏该字段，绝不显示为 0。
- 可用备用空间只在低于设备自身报告的 threshold 或存在明确 critical warning 时告警，不套用跨型号的通用阈值，也不自行定义“接近阈值”。

### 7.3 SSD 健康页面

磁盘详情增加“健康”标签，与实时吞吐分离。首屏只展示最重要的结论：

```text
JianDisk
设备未报告 SMART 故障

累计主机写入      531 TB
寿命消耗          约 7%
当前温度          41°C
介质错误          0
```

下面使用普通两列表格展示：

- 型号、固件、连接方式、容量。
- 可用备用空间与设备报告阈值。
- 通电小时、通电次数。
- 异常断电次数。
- 介质错误与错误日志条目。
- 最近 7、30、90 天新增主机写入。
- 数据最近读取时间和来源。

不把每个字段做成彩色卡片。正常值使用主文字或次级文字；只有超过设备阈值或出现新增错误时使用琥珀/红色。颜色必须配合图标和文本。

页面状态固定区分：正在读取、成功但只支持部分字段、当前连接不支持、读取失败但保留上次成功值、从未成功、设备已断开。使用历史值时首屏结论旁显示“上次读取于…”。`SMARTStatus` 缺失时不能生成“未报告 SMART 故障”；介质错误新增、备用空间越过阈值或设备明确报告的温度警告必须提升为主结论，不能被 `Verified` 掩盖。只有温度数值、没有设备警告或阈值时不自行判定异常。7/30/90 天趋势显示实际记录覆盖，数据不足时不显示 0 增长。

### 7.4 不支持的设备

USB 硬盘盒可能不透传 SMART。此时页面显示：

> JianDisk 当前连接方式没有向 macOS 提供详细健康数据。实时吞吐和容量监控仍然可用。

不要显示“未启用”，因为用户未必有可以启用的设置；不要建议反复授权。若设备直连 Thunderbolt/PCIe 后能力变化，页面自动刷新。

### 7.5 SATA 与第三方兼容层

第二阶段可以引入 `smartctl` provider，提高 SATA 和部分 USB bridge 的覆盖率。它不是首版前置条件。

已有原生 `diskutil` NVMe 字段的设备不得为了读取同一数据而依赖或内置 `smartctl`。`smartctl` 也无法保证读取不透传 SMART 的硬盘盒；只有设备覆盖矩阵证明它能增加有效数据时才进入实现。

- 固定受审计版本并遵守 smartmontools 的 GPL 分发义务，随包提供许可证与对应源代码获取方式。
- 以独立进程 provider 调用，不把 GPL 代码链接到主程序；随分发包提供许可证、对应源代码或有效获取方式。
- 只接受 JSON 结构化输出，并限制执行超时与输出大小；设备路径、命令和参数均使用白名单，不接受用户拼接的 `-d` 等底层参数。若设备访问仍需 root，复用同一 helper 安全模型并明确展示管理员批准的原因。
- SATA `Total_LBAs_Written`、Wear Leveling Count、Media Wearout Indicator 等均为厂商属性；只有型号适配表确认 raw value 语义后才展示。
- 未确认的属性保留在可导出的原始诊断中，不进入用户健康结论。

## 8. 寿命与磨损表达

### 8.1 可以展示

- 设备报告的寿命消耗百分比。
- 累计主机写入。
- FindDiskKiller 自开始记录后的每日新增主机写入。
- 最近 7/30/90 天的写入趋势。
- 介质错误是否新增、备用空间是否接近阈值。

### 8.2 条件满足后才能展示

“按当前使用强度预计剩余时间”必须同时满足：

1. 设备提供有效且发生过变化的 `PERCENTAGE_USED`。
2. FindDiskKiller 至少观察 30 个有效自然日。
3. 期间设备身份稳定，计数器单调且没有长时间缺口。
4. 磨损变化至少达到设备报告粒度，不能用长期为 0 的整数百分比外推。
5. 使用区间而非单一日期，并展示计算依据。

不满足时显示：

> 当前数据足以查看累计写入，但不足以估算剩余使用时间。

Apple 内置 SSD 没有可靠公开 TBW 时，不根据容量套用其他型号的 TBW。用户也不需要自行填写不易理解的厂商参数。

### 8.3 擦写次数

NVMe 标准健康日志通常不提供真实 NAND P/E 次数。界面默认不出现“已擦写 N 次”。只有 SATA/厂商扩展字段经过型号级验证后，才在详细信息中显示：

```text
设备报告的平均擦写次数    312
来源：厂商 SMART 属性 177
```

它不能替代寿命消耗或主机累计写入，也不能跨厂商比较。

## 9. 异常解释

FindDiskKiller 不发送系统通知、不自动弹窗。用户打开应用时，可看到以下可行动结论：

- `Codex 已持续写入 18 分钟，明显高于其最近 7 天同类时段`
- `本次追踪中，82% 的写入请求集中在 ~/Projects/find-disk-killer/.git`
- `JianDisk 最近 30 天新增主机写入 12.8 TB，比前 30 天高 64%`
- `JianDisk 新增 1 个介质错误，建议先备份重要数据`

判断规则：

- 进程异常来自进程总 I/O 的持续时间、绝对阈值与本地历史基线。
- 目录解释只在本次深度追踪有足够覆盖时出现。
- SSD 趋势来自 SMART 计数器差值，不把当前进程请求直接换算成寿命消耗。
- 同一问题只更新现有状态，不反复制造提醒。

## 10. 隐私与数据保留

- 常态打开文件快照默认只驻留内存。
- FSEvents 普通历史只保存目录身份的 keyed HMAC、变化计数和卷，不保存完整文件名。HMAC 不能还原路径；历史界面只显示当前内存映射仍能对应的可读目录，其余显示为“历史位置已隐藏”，不能伪造路径。
- 深度追踪的原始输出仅在 helper 与宿主的内存流中存在，不落普通日志。
- 会话完成后保存目录级聚合；路径默认将用户目录缩写为 `~`。
- 用户可以选择“不保留追踪结果”“保留 24 小时”“跟随普通历史保留期”。默认 24 小时。
- 文件级明细默认在会话结束后 15 分钟清除；目录级聚合按用户设置保留。
- 导出前预览是否包含完整路径、用户名、命令行和设备序列号，默认全部关闭。
- `立即清除文件活动历史` 必须在设置中可见，并同步清除相关索引与路径身份密钥。
- 不承诺 SSD 上的删除可以物理不可恢复。

## 11. 性能与响应门槛

### 11.1 常态模式

- OpenFileSampler 在空闲机器上的额外 CPU P95 小于 1%。
- 全应用总常态 CPU P95 小于 2%，内存稳定且 24 小时无持续增长。
- 单轮系统文件描述符扫描预算 250 ms；超时后停止本轮并显示覆盖不足。
- UI 不在主线程枚举进程、读取图标、解析路径或排序大列表。
- 点击导航在 100 ms 内给出选中反馈；历史内容立即显示，冷数据使用同构骨架。

### 11.2 深度追踪

- 追踪期间 FindDiskKiller + helper 的额外 CPU P95 目标小于 8%，内存小于 200 MB。
- 解析使用有界缓冲；UI 数值最多 4 Hz，图表与明细列表最多 1 Hz，不逐事件刷新 SwiftUI。
- 事件积压超过预算时优先停止文件级明细，保留目录聚合；仍无法跟上则结束会话并标记结果不完整。
- 任何追踪故障不得阻塞或拖慢被观察进程。
- 停止操作 300 ms 内给出反馈，2 秒内完成子进程回收与可查看结果固化。
- 性能统计必须包含 `fs_usage` 子进程和内核 tracing 开销，并固定 P95 统计窗口、硬件/OS、工作负载、事件率、队列字节上限与降级阈值。

## 12. 无障碍与本地化

- 10 种现有语言必须同步增加完整句子键，不拼接“进程 + 状态 + 目录”。
- `读取请求`、`写入请求`、`正在访问`和`最近变化`在每种语言中保持不同语义。
- VoiceOver 行摘要包含应用、目录、读写请求、时间范围和证据来源。
- 图表提供同一时间窗口的等价表格。
- 支持键盘开始/停止追踪、切换结果、展开目录、排序和在 Finder 中显示。
- 增强对比度、降低透明度、浅色/深色、大字号、最长翻译和最小窗口全部进行截图检查。
- 提示卡不依赖透明材质；文本不得与底层列表重叠。

## 13. 测试与数据门槛

### 13.1 libproc 夹具

- 受控进程分别以只读、只写、读写方式打开固定文件，打开模式识别正确率 100%。
- 打开、关闭、重命名、删除后仍持有 FD、符号链接和 APFS Data 卷路径均有测试。
- PID 复用不得继承旧路径。
- 当前用户拥有的受控进程路径召回率至少 99%；权限不可见必须显示缺口而不是空结果。
- 覆盖用户态 `O_RDONLY`、`O_WRONLY`、`O_RDWR`、`O_EVTONLY` 打开行为，并验证返回的内核 `FREAD/FWRITE` 位；同时覆盖未知 flags、FD 关闭复用、PID 复用、EPERM/ESRCH、非 UTF-8 与预算超限。

### 13.2 FSEvents 夹具

- 创建、修改、重命名、删除和目录批处理均能显示正确变化目录。
- 注入 UserDropped/KernelDropped 后立即形成缺口并重新建立 stream。
- 测试不得断言 FSEvents 能提供进程身份或字节数。

### 13.3 深度追踪夹具

- 每个支持的 macOS 大版本保存经过脱敏的 `fs_usage` 格式夹具。
- 覆盖 open/read/write/pread/pwrite/close、错误调用、短写、FD 复用、进程退出和截断路径。
- 对成功、无短写的受控调用，请求字节聚合与测试程序提交的请求字节误差不超过 1%。
- 路径覆盖率低于 95% 时，目录摘要必须显示“结果不完整”，且不得生成“主要集中在某目录”的结论。
- 路径覆盖矩阵必须包含 Codex、Claude、Xcode、Git、npm/pnpm、SQLite、大文件复制、rename/unlink 和子进程快速创建；分别记录完整路径、可靠 FD 补全和未定位比例。
- 解析器遇到未知核心格式时 fail closed，不能把错误列解析为字节数。
- helper 被终止、宿主退出、睡眠、超时和用户停止后无残留 `fs_usage` 进程。
- 指定目标夹具覆盖单文件、普通目录、多子文件、带空格与 Unicode 的路径、超长/截断路径、`/foo` 与 `/foobar` 边界、大小写敏感卷、符号链接、硬链接、rename/unlink、无路径 FD 和卷身份变化。
- read/pread/readv 与 write/pwrite/writev 的成功记录分别验证 `B=` 请求量；errno、未知列、坏行和系统版本格式变化必须 fail closed。`fs_usage` 的线程 ID 未经 root 侧映射时不得作为 PID。
- 高事件率测试固定记录输入行速率、内存上限、250 ms 聚合桶、2–4 Hz UI 快照、背压和 dropped-event 数；消费者变慢不能导致无界 stdout 或 SwiftUI 逐事件刷新。

### 13.4 SSD 夹具

- 128 位 SMART 计数器组合、单调差值、重置和溢出有确定性单元测试。
- Data Unit 转换固定为 512,000 bytes，并与已知原始样本核对。
- `PERCENTAGE_USED = 0/1/99/100/255` 均有正确且不夸大的文案。
- Kelvin 温度只有通过 capability 检查才转换。
- SMART 字典缺失、部分字段缺失、USB 不透传、计数器回退和设备更换均不得产生虚假零值或巨大增量。
- 同型号同容量换盘、换 USB/Thunderbolt 外壳、重启后弱身份和设备序列不可见均不得继承错误趋势。
- 支持矩阵至少包含 Apple 内置 NVMe、第三方 PCIe/Thunderbolt NVMe、USB NVMe bridge、SATA SSD 和不提供 SMART 的外置设备。

### 13.5 用户体验验收

- 90% 目标用户能在 30 秒内找到某应用当前访问的前三个目录，并理解这里没有目录字节数。
- 85% 用户能独立完成一次 1 分钟追踪，并正确说出写入请求最多的目录、请求平均和峰值。
- 85% 用户能正确解释“写入请求”不等于物理落盘。
- 90% 用户能找到 SSD 累计主机写入与寿命消耗，并不会把它理解为 NAND 实际写入或精确报废日期。
- 权限被拒绝后，用户仍能继续使用当前功能，并能说明缺少的只有限时深度追踪或受保护路径。
- 所有核心任务在追踪进行中仍能被侧边栏切换打断，不能出现不可取消骨架或模态等待。

Gate 顺序固定为 `DISTRIBUTION-0 → TRACE-SECURITY → TRACE-DATA → TRACE-PERF → UI 集成`。每个 Gate 固定保存构建产物、执行命令、OS/架构/硬件矩阵、负责人和失败回滚结论；基础单元测试通过不能替代任何深度 Gate。

## 16. 评审与签发规则

本方案需要至少三类独立评审循环：

1. **macOS 平台与数据评审**：libproc、FSEvents、`fs_usage`、SMAppService、SMART 字段和系统版本边界。
2. **产品与交互评审**：任务路径、文案、空/加载/权限/失败状态、信息层级、视觉一致性和无障碍。
3. **交付与安全评审**：helper 权限、XPC、隐私保留、性能门槛、测试矩阵和发布 Gate。

每轮评审必须记录具体问题、严重级别、回写位置和复审结论。存在以下任一问题时不得签发：

- 把推断展示成实测。
- 用户看到无法采取行动的状态或入口。
- 权限拒绝后核心应用不可使用。
- 列表刷新、骨架或悬停阻止点击。
- SMART 缺失被展示成零或健康。
- 未满足条件却预测具体 SSD 剩余年限。
- helper 可以执行非白名单命令或长期记录原始路径。
- 10 种语言、VoiceOver 或最小窗口出现内容遮挡。
